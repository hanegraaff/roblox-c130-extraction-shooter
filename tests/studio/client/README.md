# Client TestEZ runner

This package’s `init.client.luau` maps to the test-only `StarterPlayerScripts.ClientTests` LocalScript and runs the [client specs](../specs-client/README.md) automatically during Play.

Read `Players.LocalPlayer.PlayerScripts.ClientTests:GetAttribute("ClientTestReport")` in the **client** context. JSON includes suite/environment/seed, discovered/passed/failed/skipped/errors and the actual client `userId`. A missing report, zero discovery or any failed/skipped/error case is incomplete or failed evidence. TestEZ also writes useful details to Studio Output.

Use the [Studio procedure](../../../docs/testing.md#run-the-studio-smoke-suites) to collect both context reports and stop/restart. A server report cannot replace client GUI/replication assertions. This runner and its dependencies never enter the release mapping.

After the foundational specs, `RoundHarness.run()` starts a bounded discovery task for the test-only P03 transport. Automated probes observe the actual LocalPlayer role/life/deadline, RoundHUD and spectator/lobby CameraSubject, send production surrender intent and disconnect through StudioTestService. The listener disconnects when its transport is removed. These observations supplement the current three client TestEZ cases; they are not additional foundation-case counts.

`HumanTestPanel.start()` discovers the test-only session and creates one bottom-right Studio panel. Its role/duration/start/reset/location buttons send bounded server intent tagged with sequence and generation. Server feedback and authoritative attributes drive labels. The GUI persists through character respawn; stopping or removing the session disconnects listeners, cancels pending discovery and destroys the panel. It is never mapped into release builds.

`AircraftHarness.run()` adds P04 actual-client probes through its own excluded transport. It measures replicated canonical pose error, map presence/tangent/altitude, inward operator view, acknowledged weapon/FOV/reticle coherence, singleton ThermalHUD/effect/highlights, original FOV/mouse restoration and real LeaveTest departure. Its transport listener disconnects on removal. Failed probes retain their collected observations. Reticle failures include numeric pixels, viewport/GUI sizes, rendered-frame counts and role/phase/life context while preserving the existing bounds and render timing. Both aircraft harnesses also require the actual drawn reticle center, converted back to viewport space with current GuiInset, to agree with ray pixels within one pixel. These observations supplement the current three client TestEZ cases; rendering occlusion still requires actual visual review. Follow the [P04 procedure](../../../docs/testing.md#run-the-p04-aircraft-harness).

`ExpandedMapHarness.run()` handles P13's excluded test transport. Each actual client compares replicated static map identity/count/shape/flags exactly and CFrame/size numerically within 0.001, checks all building panel IDs/Intact states, queries the eight terrain apex materials/elevations and observes the expanded-perimeter aircraft. It returns the separate foundational client report with each probe and disconnects when transport is removed. These probes cover initial, reset and late-join observations; they do not prove firing, destruction or panning.

`AircraftPanHarness.run()` adds P14 actual-client fixtures. After foundational reports, it stops the ordinary entrypoint through its owned teardown and starts the same production RoundPanel with a nonyielding signed directional-pan/raw-aim-pointer/recenter/profile-intent provider. It never assigns focus. Probes retain same-frame camera/viewport/reticle/surface metadata, require real nonflat Terrain slopes and each requested building’s StoryId `02` panel, sample 585 native CFrames across disk-edge/orbit combinations, and check full-orbit inward bounds at both acknowledged FOVs. It also checks Ground-camera isolation, rejection, blocked/outside input, recenter, thermal configuration and role-loss cleanup. The transport and fixture panel listeners are removed together.

These written fixtures require the [P14 two-client procedure](../../../docs/testing.md#run-the-p14-panned-targeting-harness). Injected input is automation evidence, not physical input evidence; actual native WASD/touch-pad/aim/keys/buttons, viewport/readability and rendered occlusion require an ordinary session with the default UserInputService path. The current ordinary smoke passes all three client cases, including actual PointerGui interaction through the production input adapter. A separate actual raster probe confirms fractional/odd-viewport/clamp samples use identical drawn and ray pixels. Earlier native preview/capture observations do not close the corrected-candidate engine, full-orbit native-input and rendered/UI acceptance gaps.

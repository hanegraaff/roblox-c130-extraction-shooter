# Server TestEZ runner

This package’s `init.server.luau` maps to the test-only `ServerScriptService.ServerTests` Script. During Play it waits up to ten seconds for actual bootstrap status and, separately, up to 60 seconds for the first real client, then runs the complete nonempty [server specs](../specs-server/README.md) through locked TestEZ. `workspace.ServerTestStartup` records JSON status, elapsed seconds, budget seconds and actual client count roughly once per second and on arrival or timeout. On first-client timeout it publishes a failed zero-discovery `ServerTestReport` and errors; zero discovery is not a pass. On source `0ab3607`, a separate zero-client Studio `Run` produced the expected failed timeout report after 60.043791 seconds; this is negative-path evidence, not a passing smoke. A first client arriving after ten seconds remains unverified. On `0ab3607`, P06Team passed after a controlled same-session runner restart with three actual players already connected; that result is not a clean native cold-start pass. This budget does not change harness roster or gameplay deadlines.

Read `workspace:GetAttribute("ServerTestReport")` in the **server** context. Its JSON includes suite/environment/seed, discovered/passed/failed/skipped/errors and actual `clientCount`. Zero discovery, any skip/failure/error, missing readiness or a missing report is not a pass. The runner also asserts on invalid totals and sends TestEZ details to Studio Output.

Follow the [run and restart procedure](../../../docs/testing.md#run-the-studio-smoke-suites). The release mapping excludes this runner, all specs, fixtures and TestEZ.

After TestEZ passes, `RoundHarness.run()` starts the actual GameRuntime. Without automation args it starts the human test session (default next duration: 60 seconds, explicit start, solo previews). With StudioTestService args `{ kind = "P03" }`, it drives the three-round multiplayer scenario and returns structured evidence through `EndTest`. Its test transport and shortened settings never enter release artifacts. See the [harness instructions](../../../docs/testing.md#run-the-p03-multiplayer-harness) for required actual clients and reports.

`CharacterCleanup.run()` supplies the final harness regression: stop actual avatar loads while pending, assert truthful task accounting and ownership rejection, wait for drain, then acquire/stop a fresh owner. It checks automatic spawning restoration and lease/listener cleanup using real engine loads.

`LocalTestControls.start(rounds)` runs only in ordinary Studio test sessions after GameRuntime starts. One client automatically previews the battlefield after its body is ready, retaining Waiting/Lobby and a clear preview label. ServerStorage BindableFunctions `LocalTestControls.ExploreMap` and `ReturnToLobby` offer explicit navigation; they reject wrong phases, unavailable characters and non-solo preview. A heartbeat contains preview movement to the disk; cleanup disconnects it, clears the preview marker and destroys the functions. No client remote or test role override exists.

For the explicit four-case regression, start `StudioTestService:ExecutePlayModeAsync({kind = "LobbyControls"})` from Edit/plugin context. `LocalTestControlsCheck` runs the TestEZ spec after the actual runtime is ready and returns discovered/passed/failed/skipped/errors/clientCount through EndTest. This requires one actual client and covers unlocked protection, automatic preview, no active life, boundary recovery and return/duplicate rejection. The existing P03 three-round harness remains a separate gate.

`HumanTestSession.start(initialRuntime)` takes ownership of the actual runtime, human-setting transport, request budgets, role preferences and restart task. Validated requests carry an increasing sequence and current session generation. Roles and durations apply at the next explicit start/reset; existing competitive roles/deadlines are unchanged. Starts require 2–10 real clients, reject conflicting/all-Ground preferences, and select a fresh normal RoleService seed matching the chosen operator. Reset uses the real map reset path, waits for avatar work to drain and replaces the runtime. Teardown removes transport/preview controls and stops the current owner.

`HumanTestCheck` runs six one-client cases with args `{kind = "HumanTestControls"}` via ExecutePlayModeAsync, or four two-client cases with `{kind = "HumanTestMultiplayer"}` via ExecuteMultiplayerTestAsync(2,args). Both return real TestEZ totals through EndTest. Tests cover invalid/replayed/stale-generation requests, preview role anchoring, duration choices, solo rejection, conflicts, exact requested real roles, reset/restart and cleanup.

With args `{kind = "P04"}`, RoundHarness delegates to `AircraftHarness.run()`. It starts two actual clients with the production 90-second orbit and checks six scenarios: both profiles/inward camera, rejection immutability, real thermal obstruction fixtures, nine paired pose samples across the full orbit, reset/reentry/input/effect cleanup, and actual operator departure/teardown. Transport/fixtures are test-only and removed before EndTest. See the [P04 procedure](../../../docs/testing.md#run-the-p04-aircraft-harness) for launch, reports and convergence bounds.

With args `{kind = "P13"}`, RoundHarness delegates to `ExpandedMapHarness.run()`: two actual clients observe map/terrain/panel/aircraft agreement, a real ground avatar traverses all three upper floors, two perturbed round resets restore the source map, and a third actual late client remains a spectator. The fifth scenario verifies repeated teardown. Every wait is bounded and an early failure remains in the structured EndTest report. Teardown runs in an independent protected check after earlier scenario failure, so a failed late-client launch does not suppress its resource assertion; teardown success does not turn an earlier failure into a pass. See the [P13 procedure](../../../docs/testing.md#run-the-p13-expanded-map-harness).

With args `{kind = "P14"}`, RoundHarness delegates to `AircraftPanHarness.run()`. It expects six scenarios with two initial actual clients: full 90-second orbit at each FOV and 28 surface probes, zoom/rejection/Ground-camera coherence and overlapping operator pan/Ground humanoid movement, blocked/outside input and recenter, slope/upper-floor thermal configuration, reset/new-round/actual operator departure, and drained idempotent teardown. All client waits are bounded, failed observations survive in EndTest, and teardown runs after earlier failure. The fixture transport never enters release builds. Require actual execution reports and separate native-input/rendered/viewport review; see the [P14 procedure](../../../docs/testing.md#run-the-p14-panned-targeting-harness).

`AircraftPanHarness.run(arrivalRegression?, finish?)` keeps SDK EndTest delivery by default. A nonyielding `finish(report)` receives the same structured report after owned cleanup. For the manual Studio route, a temporary server-only `DevelopmentSettings.ManualHarness = "P14"` dispatches before HumanTestSession only in Studio with nil SDK arguments; its callback writes actual Server workspace `ManualP14Report` and `ManualP14Invocation`. The marker is absent from source/release defaults and must be restored to nil in Edit. The [manual procedure](../../../docs/testing.md#manual-studio-server--clients-route) preserves reports, ends owned children through actual-server EndTest and confirms Edit; generic MCP Stop alone did not end that context. This route retains the same two-client/six-case requirements and has not yet completed on the current source.

With args `{kind = "P05"}`, `RoundHarness` delegates to the test-only `CombatHarness`. It starts a normal GameRuntime with two actual clients and uses real fire/selection transport, disposable level fixtures and role observations to exercise weapon readiness, rejection, swept collision, elimination and reset. It returns eight named cases and observations through EndTest. A timeout before both clients connect, failed case or early exit is incomplete evidence; verify the candidate's exact case list and reports. See the [P05 procedure](../../../docs/testing.md#run-the-p05-gunship-combat-harness) and [plan](../../../plans/05-gunship-combat.md) for source-specific results and gaps.

With args `{kind = "P06"}` or `{kind = "P06Team"}`, the test-only `GroundCombatHarness` runs real two- or three-client ground-combat scenarios through normal runtime ownership, with server-only rocket fixtures. Current source-specific results and gaps are recorded in [P06](../../../plans/06-ground-combat.md); current-source P06 passed 10/10 with two actual clients, and P06Team passed 7/7 after a controlled same-session runner restart with three already-connected actual clients; the user also reviewed firing. A launch timeout, failed completion or missing client is not a pass.

With args `{kind = "P07"}`, RoundHarness delegates to `DestructionHarness.run(finish?)`. It requires exactly two initial actual clients, uses actual GameRuntime and production gunship fire/selection transport, then pauses at `P07Stage = { stage = "AwaitingLateJoin", ... }` for a genuinely new third PlayerAdded after damage. The checkpoint has a 240-second bound. Seven scenarios cover rejected traffic, heavy 3/6 and nine-second 30mm progression, actual damaged-opening traversal, state agreement/debris expiration, same-round late spectator and two resets during pending work/fragments. A bounded production impact observer records actual accepted `firedAt`, panel identity and rule snapshots; receipt and client-send diagnostics do not authorize damage. The 61-request burst uses a 0.18-second test send interval, requires every request to become an accepted on-panel impact within the unchanged cadence/gap bounds, asserts zero first-hit credit and checks that the stage transition occurs only after at least nine accepted seconds. After flights and the idle barrier settle, client probes compare a frozen progress snapshot. The wall-opening fixture forecasts a clear exterior approach, then rechecks the actual first hit and readiness before each shot. Missing clients/timeouts/early failure remain failures; written scenarios do not establish execution.

A Studio-only `DevelopmentSettings.ManualHarness = "P07"` with nil SDK args invokes the same harness through native Server & Clients. Its finish callback preserves `ManualP07Invocation`/`ManualP07Report` in the actual Server workspace instead of calling SDK EndTest. `P07MultiplayerReport` and `P07Stage` retain result/checkpoint data. Start two clients, add the third only at the checkpoint, preserve reports before **End Session**, then restore the Edit selector to nil. The marker is absent from authored source/release defaults. See the [P07 procedure](../../../docs/testing.md#run-the-p07-destruction-harness) and [plan](../../../plans/07-destruction.md) for exact requirements and actual results.

A direct low-level zero-client `RunService:Run()` can leave runtime Instances as well as report attributes in Edit, including BootstrapStatus. Normal Play/Stop is preferred. If running that negative probe, snapshot/restore every affected owned Instance and attribute, verify absence of confirmed probe-created stale owners and retain its expected failure separately; see [Edit cleanup](../../../docs/testing.md#preserve-edit-state-around-a-zero-client-run).
